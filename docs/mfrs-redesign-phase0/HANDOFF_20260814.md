## 二、本次修复的四件事

### 1. 🎯 事件纪要正文被覆写成 `SP0001`（根因，`8fa1202`）

**现象**：`insertRow` 写入 320 字纪要正文，**150 毫秒内**被替换成 `SP0001`（6 字）。其余五列完好。事件纪要是 14 表中唯一 `exportConfig.enabled=true` 的表，正文即注入提示词的长期记忆 → AI 每轮读到的历史只剩一串编号。

**根因**（`vendor/shujuku-sp-fork/index.js` `getSummaryIndexColumnIndex_ACU`）：

```js
const headers = table.content[0].slice(1);   // ['纪要编号','时间跨度','关联事件','概览','纪要']
let idx = headers.findIndex(h => /编码|索引/.test(h));   // 「纪要编号」不含"编码/索引" → -1
if (idx === -1) idx = headers.length - 1;                // 危险回退：猜最后一列 = 正文列
// → applySummaryIndexSequenceToTable_ACU 把正文覆写成 SP000N
```

`isSummaryOrOutlineTable_ACU` 硬编码把「事件纪要」认作总结表，自动编号 `isSpecialIndexLockEnabled_ACU` **默认开启**。列名差一个字（编号 vs 编码）导致匹配失败，回退去改最后一列。

**修法**：正则补认「编号」；删除"猜最后一列"回退，识别不到返回 `-1` 放弃自动编号。旧 ACU 的「编码索引」列名兼容性保留。

### 2. AI 写表列名/枚举硬约束（`bbf98fb`）

`世界书/规则/数据库联动规则.txt` 新增「六、写表硬约束」：14 表完整中文列名清单、常见英文列名错误对照（`related_event→关联事件`、`identity→身份`、`当前位置→所在地点` 等）、13 组枚举白名单、固定行表 `match row_id` 约束、事件纪要正文专项。

**实测效果**：`COLUMN_NOT_FOUND`、`CHECK_IN_VIOLATION`、`NOT_NULL_VIOLATION` 全部消失，丢写率从 25-40% 降到个位数。

### 3. 表名剥离「序号:」前缀（`782e27f`）

vendor 以 `序号:表名` 注入提示词，AI 照抄写进 `plan.table`（`9:事件纪要`），`findTable` 只做精确匹配 → 真页一轮 **10/10 计划全废**。修法：精确匹配失败后剥 `^\d+[:：]` 重试，剥完仍须命中真实表。

### 4. 防御与探针（`bbf98fb` + `8f892b1`）

- vendor native `<tableEdit>` 路径（`parseAndApplyTableEdits_ACU` 的 insertRow/updateRow）补事件纪要守卫，判定与 SQLite/前端三方同源，拒绝时打调用栈
- 前端 `table-change-adapter.ts` `buildTables`：空 `ddl` 不再覆盖模板 DDL（否则整表约束静默失效）
- 前端 `index.ts`：包装 `AutoCardUpdaterAPI` 写方法做审计（只观测不拦截），自等 API 就绪 + 与 autofix 成败解耦

> 注：守卫与探针**对根因 #1 全程静默是正确的**——污染发生在写入成功之后的 vendor 内部改写，不经任何写入 API。它们的独立价值是挡住 AI 把编号写进正文。

## 四、给下一位的关键经验

**❗ 不要浪费用户的对话轮次做验证。** 上一会话最大的低效：因为"绝不主动调 LLM API"的约束，把整个验证流程都交给用户手动跑，连烧四五轮。实际上大量缺陷（包括本次根因）**完全不需要 LLM 参与**，可以在页面上自建复现：

```js
// 零 LLM 成本的复现范式：写入 → 定时轮询观察降解
await api.insertRow({ tableName: '事件纪要', skipChatSave: true, silent: true, data: {...} });
for (const wait of [50,100,150,300,500,1000,2000,3000]) { /* 采样 read() */ }
```

早期我做过一次活体写入但**读回太快**（立刻就读），错过了 150ms 的降解窗口，误判"写入正常"，白白多花三四轮。**观察异步降解必须带时间轴采样。**

**真页验收三件套**（每次都要查，历史上多次踩坑）：
1. **当前是哪张卡** —— 发布版指向 CDN 旧代码，改动一行都不生效（曾在发布版上白测两轮）
2. **服务器 dist 是不是新的** —— 直接 `fetch(url + '?bust=' + Math.random())` 校验特征字符串
3. **代码是否真的挂上了** —— 例如探针要检查 `String(api.insertRow).includes('chronicle-audit')`，不能假设"我写了就生效"

**排查异步污染的有效工具链**（按代价从低到高）：
1. 自建复现 + 时间轴采样（零成本，优先）
2. 包装公开 API 记录参数与栈
3. `exportTableAsJson` 在 native 模式返回**活引用** → 可在数据结构上设 Proxy/setter 抓元素级写入
4. 给 `chat[i].TavernDB_ACU_IsolatedData` 装 setter 抓落盘调用栈

**判定"写坏"还是"读坏"**：对比内存视图与 `chat[i].TavernDB_ACU_IsolatedData` 快照——本次快照里就是 `SP0001`，直接排除了读回解析问题。

**验证陷阱**：`exportTableAsJson()` 显示 14 表可能只是 fallback 的模板 padding，不代表物理表存在；验收必须看**各表数据行数 + 控制台有无 not found/预检失败**。

**上游 API 噪音**：`[剧情推进] Bad Gateway` / `CRUD Plan 上游 API 网关错误` 是用户的 API 抽风（会触发 15 秒冷却），与卡无关，会导致本轮填表不完整——不要当成 bug。
